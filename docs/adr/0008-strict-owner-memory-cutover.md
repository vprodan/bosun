# 0008 · Strict owner memory plan, apply and reconciliation

**Status:** Implemented for strict prepared layouts, reviewed initial preparation and independently bound incomplete-attempt recovery; process drain/restart, general restore and orphan disposition remain held. **Date:** 2026-10-06.

## Decision

The owner CLI exposes explicit commands through `lib/memory/sqlite.ts → src/adapters/memory/sqlite-owner.ts → sqlite-cutover.ts`:

```text
bosun memory cutover prepare-plan [--create-view-directory] [--create-backup-directory] [--json]
bosun memory cutover prepare --plan TOKEN --clients-stopped [--json]
bosun memory cutover plan [--retain-unreferenced] [--json]
bosun memory cutover apply --plan TOKEN --clients-stopped [--json]
bosun memory cutover reconcile --plan TOKEN --source-id UUID --clients-stopped [--retain-unreferenced] [--json]
bosun memory cutover recover-plan --source-id UUID [--retain-unreferenced] [--json]
bosun memory cutover recover --plan TOKEN --source-id UUID --clients-stopped [--retain-unreferenced] [--json]
```

Only this explicit owner path can call initial `cutoverMemory`; ordinary memory, hook, MCP and server startup never install or recover a floor. No new domain port is added, and registered native handles remain private. Explicit publication remains a separate `memory publish` READY operation, per [ADR 0006](0006-explicit-public-memory-publication.md). A successful apply/reconcile/recover returns HOLD, source/attempt UUIDs and generation plus explicit restart/publication/binding requirements; no owner rows, audit values, backup digest or artifact paths are returned. Recovery also reports preservation of the prior verified reference and the count of separately acknowledged unreferenced files with unverified ownership.

## Filesystem-only plan and permissions

Ordinary strict planning and preparation never open SQLite. All planning avoids mutable-primary SQLite, directory/storage creation, migration, chmod, floor installation, publication and writes to `MEMORY_SOURCE_ID`. Strict planning checks canonical paths, owner identity, exact 0700 directories/0600 single-link files, distinct source/view/backup storage, presence, bounded sizes, primary/view/backup minimal 20-byte SQLite headers and the optional 32-byte WAL header. Mutable primary/WAL bytes are never copied or fully hashed. The primary must have WAL header mode; view/completed referenced backup must have rollback header mode. Dangling/symlink/hardlink paths, pending journals, view WAL/SHM, unexpected names, missing/unsupported layouts and ambiguous artifacts are held. Remote `MEMORY_URL` selection is rejected before inspecting local memory storage. Explicit recovery/retention planning additionally inspects only the rollback view natively, as described below.

Strict cutover planning reports known permission and missing-layout failures as `BLOCKED`, a finite target/reason and, for mode failures, current/required octal modes. It returns no usable token or source UUID and makes no repairs. For example a legacy `.bosun` directory with 0755 is reported as `primary-directory: permissions (current 0755, required 0700)`. The owner can separately review the preparation workflow below before obtaining a new strict cutover plan.

An absent view with an empty backup directory produces an apply candidate. A present rollback-header view with exactly one UUID-named completed rollback backup produces a reconcile candidate. **Schema, floor and clients are always labelled unverified.** Header evidence cannot establish an owned floor/gate or prove a valid backup. Native apply/reconcile validates exact schema and owner gate/floor/backup identities and digest before changing them. A candidate can therefore fail native validation without being adopted.

Without the explicit recovery/retention options, the one-completed-backup rule still holds incomplete, rolled-back and multi-artifact storage. The bounded recovery workflow below permits verified gate references and explicitly retained unreferenced files; it does not establish orphan ownership or provide general restore/disposition.

Existing CLI configuration initialization remains unchanged: `config.load` may create `.bosun/config.env` before dispatch. The operation itself is read-only; **the entire CLI is not a zero-IO claim**. Footprint tests pre-seed configuration.

## Reviewed initial layout preparation · 7b2c2a

`prepare-plan` inspects only the initial absent-view layout, without opening SQLite or making changes. It reports every exact owner-only path/action: known primary/view/backup directories at 0755 or 0750 can narrow to 0700, and the primary plus existing WAL/SHM single-link files at 0644 or 0640 can narrow to 0600. Already strict modes need no action. Only explicit `--create-view-directory` and `--create-backup-directory` flags permit creation of the corresponding missing leaf at 0700 under an existing canonical owner-owned parent. There is no recursive creation/chmod, chown, database creation/migration, floor installation, publication, binding or service action. Other `.bosun` files, including configuration, receive no permission changes.

Every existing view is held before any repair, including a valid old READY view: narrowing its directory could otherwise silently make it eligible. View and backup directories must be empty. Unknown/orphan inventory, pending primary/view journals or view WAL/SHM, symlink/dangling/hardlink/identity aliases, unowned paths, unsupported headers/sizes and any mode outside the exact lists above are held. This slice never adopts, copies, erases or overwrites an artifact. A missing ancestor is held rather than recursively created. Existing WAL/SHM may be narrowed only on their pinned identities; they are never copied or erased.

The finite five-minute editable preparation token binds paths, explicit creation flags, UID/device/inode/mode, sizes/nanosecond timestamps, minimal primary/WAL headers and empty inventories. **All** source/WAL/SHM timestamps remain bound here; no SQLite housekeeping waiver applies because preparation never opens SQLite. Tokens remain review/freshness bindings rather than authorization seals, ownership proofs or content hashes. Action paths occur only in the explicit owner plan/receipt, with no model or telemetry route.

`prepare --plan TOKEN --clients-stopped` requires unchanged complete preflight before its first effect. It opens every existing finite target and creation parent with `O_NOFOLLOW`, adding `O_DIRECTORY` for directories, and retains those descriptors through the operation. Before and after each action, it rechecks descriptor and canonical path identity, ownership, modes, timestamps, headers and inventory. Permission changes use `fchmod` on the checked descriptor. Only the expected mode/ctime change is accepted; approved leaf creation accepts only its parent's expected size/mtime/ctime changes after validating the new leaf's identity/ownership/0700 mode. All other planned metadata stays bound. New leaves are checked against raced-existing paths and symlink/identity replacement. Absolute-path directory creation is a trusted-application protocol; these checks do not establish isolation from arbitrary malicious same-user filesystem races.

Success returns `PREPARED`, reviewed actions, operator attestation and a fresh-cutover-plan requirement; schema/floor/clients remain unverified and no source UUID is installed. Keep clients stopped and obtain a new `cutover plan` before apply. There is no broaden-on-failure rollback and no deletion of created leaves. Any failure or lost receipt can leave partial/conservative mode or creation effects: inspect and obtain a fresh preparation plan. Owner-held descriptor close failure attempts one best-effort retry but still returns a finite failed/uncertain receipt; continued native failure does not prove descriptor release. Partial fchmod/mkdir and identity replacement tests qualify conservative behavior, without a process-drain, hostile-race or storage-durability claim.

## Independent plan identity and admission freshness

An apply plan generates the future random source UUID **before mutation** and includes it in the result/token. Save it independently before applying. The initial primitive uses that exact UUID, so a committed floor with a lost/uncertain receipt can later reconcile against the saved initial plan identity. A reconcile plan does not learn an expected source UUID from the candidate view; `--source-id` is an independently saved owner expectation, required even when configuration already contains a binding. Recovery requires this independent expectation at both planning and mutation and binds it into the token.

The bounded base64url token contains only version, operation, source UUID/null, retain acknowledgement, issued/expiry times and a metadata/header fingerprint. The fingerprint binds canonical configured paths, device/inode/owner/mode, data-file size/nanosecond modification/change times, minimal headers and backup inventory. It is **review/freshness binding, not a cryptographic authorization seal or proof of client ownership/drain**. An owner can modify it. It is not a content-derived private-record or whole-backup digest. Tokens have a five-minute admission window; malformed/extra fields, invalid clocks, future/expired tokens, unexpected CLI flags/positionals and duplicate options fail with finite errors.

Apply rechecks the token against filesystem state before opening mutable SQLite. After actual primary `BEGIN IMMEDIATE` and exact schema/floor/gate validation, a narrow synchronous expectation seam compares apply's absent floor/gate or reconcile's exact independently supplied source UUID against **both** floor and gate. It then rechecks filesystem freshness before any HOLD, backup reservation, gate DML or floor DML. There is no handle exposure or asynchronous validation callback. Admission remains continuous across the original native backup/floor transaction, per [ADR 0005](0005-explicit-memory-writer-floor-cutover.md).

Native open of a closed WAL primary was measured to create a zero-byte WAL and a canonical 0600/single-link 32768-byte SHM. Only paired absence at the initial plan permits that exact admitted layout. Existing WAL content/identity/timestamps remain bound; existing SHM identity/owner/mode remain bound, while SHM content/timestamps are native lock housekeeping. Source-directory identity/mode is bound, while its directory timestamps are excluded because creation of native sidecars changes them. View/backup directory and file freshness remains exact. No pre-existing sidecar replacement is waived. This is a trusted-application filesystem protocol: metadata cannot prove creator identity if a same-user adversary replaces newly created sidecars; no such hostile-ownership claim is made. The TTL checks admission, and does not interrupt or retract an admitted long native backup/cutover at expiry.

## Owner operation and uncertain receipts

The owner must stop every memory/MCP/docs/server authority and independently establish any needed process drain. `--clients-stopped` records **operator attestation**; SQLite write admission does not prove all clients stopped, cached handles drained or host acknowledgement. The command performs no service/host discovery, process stop, restart, install or personal configuration binding. A live native fixture intentionally demonstrates that an attested command can succeed while a cached writer remains present; that writer is fenced after floor installation.

Keep authorities stopped through initial apply and the separate explicit publication/owner-binding steps, then reopen them. Publication upgrades writer format and also fences cached v1 authorities. The owner sets `MEMORY_SOURCE_ID` from the independently saved/applied source UUID; the default stays blank. READY reading and non-expiring delivery still require [ADR 0007](0007-bound-public-memory-reader.md)'s exact binding/lease checks. No automatic republisher, daemon freshness scheduler or finite-expiry delivery solution is introduced.

Reconcile is a **mutating owner operation**: it reconciles an existing committed floor, preserves source epoch/generation and backup/view identity, and explicitly revokes an existing v2 READY publication to HOLD. Wrong independent source identity is rejected under native admission before that revocation. Reconcile is not a status read and cannot fabricate a new epoch from a candidate view. It never installs a missing floor or blindly repairs a rolled-back attempt.

Native post-floor/cleanup/receipt failures can leave a committed floor without a success receipt. CLI errors explicitly say the outcome may be unknown; they do not promise the primary was untouched or recommend blind retry. Save the initial plan UUID, inspect storage and obtain a fresh plan before explicit reconciliation or eligible incomplete-attempt recovery. Unknown files are never overwritten, deleted, guessed or adopted. Arbitrary same-inode WAL restoration retaining an old floor/view/binding remains unqualified; this command is not a restore protocol or storage/power-loss guarantee.

## Bounded reference inspection and explicit incomplete recovery · 7b2c2b

`recover-plan --source-id UUID` checks the primary/WAL through filesystem metadata/minimal headers only. It requires a canonical owner-only rollback view, with no journal/WAL/SHM or extra view-directory entry. A narrow owner→cutover helper opens only that view with native `readOnly`, defensive/no-extension options, `query_only`, memory temp storage, zero busy wait and EXCLUSIVE-mode `BEGIN`. The retained transaction protects exact gate/schema and referenced-artifact checks; filesystem identities/sidecars are rechecked before native close and the complete outer metadata/header/inventory fingerprint is compared afterward. Native hot or dangling journals are held without recovery. This measured view-only planning path makes no storage changes, excluding read atime; it never SQLite-opens the primary or any backup.

The gate must match the independently supplied source UUID and exact current primary/view/artifact device+inode identities. Format-1 `copying` requires a null digest and allows its bounded empty/unfinished referenced artifact without reading it. `backed` requires the completed rollback artifact's stored gate digest to match exactly. Filesystem hashing and digest bytes stay internal and are absent from helper projections, owner inventories, tokens and receipts. Applied/unknown pre-intent views and contradictory phase/digest metadata remain held. Primary schema/floor/clients remain unverified in the plan; only the inspected view/reference is labelled verified.

Directory enumeration stops after 32 UUID-named `.db` regular single-link owner-only files. Each is bounded at 64 MiB and the total at 256 MiB. Recovery also reserves capacity for one new artifact before admission: at most 31 existing entries and at least 64 MiB remaining. Unreferenced file shape, SQLite-looking bytes or ownership metadata do not prove protocol ownership. Their bytes are never opened/read/hashed or adopted; the owner sees bounded UUID/metadata/count information with ownership explicitly unverified. Unknown names, links/hardlinks, permissions, sidecars, oversized/aliased files and ambiguous views remain held. `--retain-unreferenced` acknowledges coexistence only and is required at both planning and mutation, bound in the token. A blocked recovery inventory can show these bounded metadata for review without returning a usable token.

Under fresh actual primary `BEGIN IMMEDIATE`, recover checks exact primary schema, **absent floor**, same-epoch valid format-1 copying/backed gate and current filesystem token before any artifact reservation, gate/floor DML or HOLD action. It never installs into an applied-without-floor view. It then creates a new native exact backup of the current committed source under continuous admission. A source changed by legacy writers after rollback is backed up afresh; no old snapshot is reused. The prior verified referenced artifact is automatically preserved, and the success receipt distinguishes it from separately acknowledged already-unreferenced files. No artifact is erased, overwritten, quarantined or assigned ownership.

A committed floor, including a gate still marked backed after a lost commit receipt, is rejected by recover. Use explicit plan/reconcile with the saved UUID; `plan --retain-unreferenced` verifies the existing referenced completed artifact and permits bounded acknowledged leftovers. Reconcile preserves epoch, generation and current backup, and explicitly revokes READY to HOLD. Recovery followed by registered mutation, reconciliation, explicit publication and an independently bound public reader is qualified. Ordinary memory open/hook/MCP/server still never recover automatically. General restore/epoch rotation, ownership/disposition of unknown pre-intent orphans, referenced mid-backup sidecars, external drain/restart and storage/power-loss durability remain separate gates.
